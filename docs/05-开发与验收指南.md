# 开发与验收指南

本文说明如何选择验证范围、使用 Docker 运行检查及记录验收结论。功能范围见[产品需求](./01-产品需求文档PRD.md)，生产部署见[部署手册](../deploy/DEPLOYMENT.md)。本文不是历史交付记录，也不代表当前分支已通过全部验收。

## 1. 修改与验证范围

先确认页面、接口、数据字段和预期行为，再选择对应检查；保留与任务无关的工作区改动。

| 修改类型 | 必要检查 | 文档同步位置 |
| --- | --- | --- |
| 页面与样式 | 相关前端测试、类型检查、构建；Compose 浏览器检查亮暗主题、窄屏和权限状态 | 对应功能说明 |
| API 或业务逻辑 | 对应后端测试；成功、异常输入、权限拒绝和状态冲突 | [API](./04-API设计.md)、对应功能说明 |
| 表或字段 | 后端测试；真实 MySQL 空库迁移、已有库升级和数据检查 | [数据库](./03-数据库设计.md) |
| 认证、凭据、权限或审计 | 针对性安全测试；响应、日志、快照和导出脱敏检查 | [架构](./02-技术架构设计.md)、API、产品需求 |
| 外部平台适配 | 离线契约测试；隔离真实平台验证版本、认证、读写及失败处理 | 对应兼容性记录 |
| 部署与配置 | Compose 配置解析、镜像构建、健康检查、持久化与重启 | 部署手册、`.env.example` |
| 仅文档 | 链接与文件路径检查；对照路由、Schema、ORM、迁移和配置模板 | [文档索引](./README.md) |

## 2. 自动化检查

以下 Docker 示例从仓库根目录执行，使用 PowerShell；Linux/macOS 可将路径变量和续行符替换为对应 Shell 语法。检查镜像仅供本地使用。

### 2.1 后端

生产镜像不包含测试文件和 pytest。检查时只读挂载后端源码、安装开发依赖，并覆盖启动入口，避免测试容器执行生产迁移。

```powershell
$repoPath = (Get-Location).Path
docker build -t opspilot-backend-check:local ./backend
docker run --rm --user root --entrypoint sh `
  --mount "type=bind,source=$repoPath/backend,target=/app,readonly" `
  opspilot-backend-check:local -c 'python -m pip install --no-cache-dir -r requirements-dev.txt && python -m pytest -q -p no:cacheprovider --basetemp=/tmp/opspilot-pytest'
```

针对性检查可将最后的 pytest 命令替换为指定测试，例如 `python -m pytest tests/test_ticket_api.py -q -p no:cacheprovider --basetemp=/tmp/opspilot-pytest`。测试文件以 [`backend/tests/`](../backend/tests/) 为准。

公共夹具使用 SQLite 内存库和 fakeredis，并对 MySQL 默认值及自增字段做测试适配。因此测试通过不能替代 MySQL 迁移、真实 Redis 恢复或外部平台联调。

### 2.2 前端

复用现有 Dockerfile 的 `builder` 阶段；构建阶段已执行生产构建，随后运行类型检查和前端测试。

```powershell
docker build --target builder -t opspilot-frontend-check:local ./frontend
docker run --rm opspilot-frontend-check:local sh -c 'npm run type-check && npm run test'
```

已安装本机运行环境时，也可在 `backend/` 执行 `python -m pytest -q`，在 `frontend/` 执行 `npm run test`、`npm run type-check` 和 `npm run build`。Windows 若拦截 `npm.ps1`，使用 `npm.cmd`。

## 3. Compose 集成验收

### 3.1 准备环境

- 使用隔离工作树和验收数据，确认端口、容器名、网络及数据卷与现有服务不冲突。仅修改项目名不一定能隔离固定的 `container_name`，应检查最终配置。
- 依据 [`deploy/.env.example`](../deploy/.env.example) 创建被 Git 忽略的环境文件，生成独立的数据库密码、JWT 密钥、加密主密钥和管理员初始密码。
- 保留数据卷再次启动时，复用原数据库密码和加密主密钥。验收环境不得复用生产数据库或未经授权的远端写入凭据。

在隔离环境的 `deploy/` 目录执行：

```powershell
docker compose config --quiet
docker compose up -d --build
docker compose ps
curl.exe --fail http://127.0.0.1:8080/healthz
curl.exe --fail http://127.0.0.1:8080/api/v1/ping
```

示例端口为 8080；设置 `NGINX_HTTP_PORT` 后须相应调整访问地址。API 启动时执行迁移和幂等种子，Worker 等待 API 健康。首次登录按提示改密并完成 MFA；不要转发包含初始密码的启动日志。

[`docker-compose.acceptance.yml`](../deploy/docker-compose.acceptance.yml) 是应用配置场景的专用覆盖文件，包含固定容器名、地址和 DNS 覆盖，不是通用验收模板。使用前核对并调整这些值。

### 3.2 业务检查

按本次修改选择检查项；涉及完整业务链路时至少覆盖以下流程。

| 领域 | 验收要点 |
| --- | --- |
| 登录与权限 | 本地/SSO、改密、MFA、密码重置；无权限时菜单、页面和 API 一致拒绝 |
| CMDB 与资源 | 主机/应用关联、导入导出、删除保护；凭据不回显；作业主机连接与启停 |
| 模板与工单 | 应用绑定仅作台账；模板与流程启停、参数预生成、快照、审批、撤回及并发控制 |
| 执行与日志 | Shell/Playbook、超时与失败策略、暂停/恢复/中止、实时及历史日志、Worker 重启恢复 |
| 通知与审计 | 六类通知事件、渠道映射、模板 JSON、失败重试、站内信、审计查询导出及保留策略 |
| 域名管理 | 公网 Zone 发现/绑定、快照、只读记录、TTL、变更预览、漂移和失败保留旧快照 |
| 应用配置 | 参照[使用与验收说明](./应用配置使用与验收.md)，区分审批通过与发布成功 |
| 工作台与页面 | 指标权限裁剪、数据周期、深链接、空态、亮暗主题及窄屏布局 |

外部写入检查只对明确授权的隔离资源进行。模拟平台验证与真实平台联调应分别记录，不能互相替代。

### 3.3 迁移与清理

数据模型变更须分别验证空库 `upgrade head` 和已有库升级；升级前备份，并检查迁移版本、业务数据和重复启动行为。只对照 ORM 建表或手工标记迁移版本不能视为迁移通过。

应用配置的历史验收曾遇到空库迁移重复添加 `retry_count`，当时使用按模型准备结构的验收库绕过；该记录未证明空库迁移链路通过。后续应在隔离 MySQL 中重新验证。迁移事实来源为 [`backend/alembic/versions/`](../backend/alembic/versions/)。

清理本次创建的测试账号和业务数据；停止隔离服务时使用 `docker compose down`，需要保留数据时不要添加 `-v`。不要清理其他人的服务、数据卷或工作区。

## 4. 验收结论与文档维护

验收记录应包含代码版本、环境及平台版本、实际执行的命令、通过/失败项、未覆盖范围和残留问题。不要把一次测试的数量、临时地址、账号或完整日志写入长期功能文档。

交付前检查：

- 代码、接口、迁移和文档使用一致的字段与状态名称，文档链接有效。
- 测试结论对应本次运行证据；未验证的真实平台或迁移范围明确注明。
- 未纳入凭据、环境文件、临时脚本、日志、依赖和构建产物。
- 执行 `git diff --check` 并检查实际变更范围；提交或推送遵循用户当次授权。
